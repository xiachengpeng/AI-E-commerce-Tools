# 03 融合可行性与风险评估

日期：2026-10-08。M/R 路径与证据约定见 [01](01-项目现状分析.md)；功能分类见 [02](02-功能融合对照表.md)。等级是源码基础上的定性评估，没有性能压测和外部 API 成功率样本。

## 1. 核心结论

**能融合，值得有边界地融合；不适合全量目录拼接、数据库硬合并或双方入口共同启动。**

事实：两者都是 Python/FastAPI、Pydantic 2、SQLAlchemy 2、httpx、原生 JavaScript。主项目当前虚拟环境与 SOP uv.lock 的 FastAPI 0.141.1、Uvicorn 0.52.4、httpx 0.28.1、Pydantic 2.13.5、SQLAlchemy 2.0.52 相同。

推断：统一用户入口、交换经确认的研究事实以及复用纯计算函数，技术成本显著小于全栈替换。SOP 把“应该卖什么及证据是否足够”补到主项目“如何制作营销素材”之前，业务价值成立。

限制：当前“本机主服务 + 远端研究服务”存在网络、授权与独立数据责任边界；两者都不具备成熟多用户 RBAC。此报告不构成可直接公网部署的认证审计结论。

## 3. 具体冲突、原因和解决办法

### C01 数据库并发语义不能降级

证据：M:backend/db.py:10–36 是 SQLite/SessionLocal；R:src/rabbit_hole/workbench_store.py:227 的 pg_advisory_xact_lock、314 行 row lock；runner.py:49 使用 JSONB，621/745 行 advisory lock，994 行 SKIP LOCKED；jobs.py:262 依赖租约抢占。

原因：这些机制保护项目版本、动作去重、停止/重试和多连接领取。SQLite 缺少 PostgreSQL 的锁语义，JSON 变体存在不能消除锁依赖。

建议：保留研究 PostgreSQL。未来若确需同库，另立可逆迁移方案并重写/验证锁、租约、索引、事务隔离，而不是导出几张表即可。本推荐方案不要求此迁移。

### C02 启动/导入存在真实写入与后台副作用

证据：M:backend/main.py:226–228 导入时建表/默认配置写入；231–238 lifespan清理文件。R:src/rabbit_hole/api.py:182–186 自动开启 business-actions/business-sync；Compose worker 独立跑旧 runtime_jobs。

原因：把两个 app/lifespan 叠加可能执行未完成任务、飞书同步或双队列消费者；直接 import 做审计也不只读。

建议：集成层仅用 HTTP client/DTO，不 import main 与 rabbit_hole.api。研究循环只有指定服务实例持有；增加独立环境启动门禁、明确已有队列恢复策略。未来首次联调一律空测试队列，不连接真实外部写入。

### C03 同源、防嵌入和路径

证据：R:src/rabbit_hole/workbench_api.py:103–122 host/origin/token；169–178 首页 CSP frame-ancestors none、connect-src self；workbench.html:2 使用 /workbench 绝对路径；workbench.js 固定 API 基址。

原因：主浏览器 9502 直接调用远端8000不满足同源/Origin；iframe被明确禁止；路径代理也不会自动改安全机制。

建议：在主 UI 原生渲染研究页，主后端通过**专用服务器集成接口**调用研究服务；新接口不采用浏览器 token、也不透传全部现有工作台路由。前期只读。旧研究工作台可保留普通链接打开；不要关闭 CSP 或允许所有 Origin。

### C04 集成不能扩散明文密钥入口

证据：M:backend/db.py:165,218–229 保存提供商/存储秘密；M:backend/main.py:1630–1687 可主动 reveal secret；R:src/rabbit_hole/provider_settings.py/ai_settings.py 文件私有但不加密。

原因：新增可达地址或无差别 proxy 可能把本机配置暴露到 LAN；CORS/Host 都不等同账号鉴权。SOP的公开设置只返回configured，但主 secret reveal 保留现有语义。

建议：研究集成路径白名单只允许业务数据与受控资产；绝不映射主 settings/secret 路由。服务间凭据只存服务器、日志脱敏、限制目的地址。默认经加密 SSH 隧道或 HTTPS 连接，未来授权后建立，禁止普通公网/LAN明文传服务凭据。若要求多人，另设计用户/租户/RBAC。

### C05 AI共享提供商不等于共享协议和事实可信度

证据：M:backend/routes/generation.py:124–179、ai_adapters.py:559/572 归一化响应；R:src/rabbit_hole/extraction.py:461 使用 responses.parse/text_format；verification_jobs.py:129–150 使用 chat JSON、max_retries=0、引用限定；verification.py:70–122 验原文/hash/指纹。

原因：主接口不直接返回 Pydantic parsed 对象，Gemini也不是Responses端点。路由更新、模型能力、图像/文本参数与预算会改变行为。

建议：先定义 StructuredGenerator 适配，不改变主公开响应；JSON/schema校验和source_quote验证继续在研究域。新增桥接后关闭 SDK 自动重试以避免叠加主路由重试。真实支付不确定结果不得自动再提交。某模型不支持schema时失败提示，不静默换模型。

### C06 Firecrawl同供应商、不同数据契约和重试政策

证据：M:backend/config.py:8默认/v1/scrape；services/firecrawl.py:99 的 markdown；R:src/rabbit_hole/collectors/firecrawl.py:24–27 /v2/scrape rawHtml/maxAge0，39–42 超时未知计费不自动重试，50–77 校验metadata、来源、HTTP状态与正文。

原因：rawHtml与markdown并非可互换，SOP采集结果必须保留采集方式/观察时间/来源链接；主缓存与retry策略可能违反研究的付费边界。

建议：建立 ScrapePurpose=marketing/research，两个驱动明确输出格式与policy。初期保持现有实现，统一配置入口不意味着统一缓存或解析器。不强制主升级v2。

### C07 双评分不是一个100分指标

证据：M:backend/services/scoring.py:75 调AI；main.py:458 固定公式机会分+(100-难度分)排序。R:src/rabbit_hole/workbench_domain.py:2807,2911 门槛和证据评分，3090 人工决策。

原因：主项目分数本身并非全程确定性客观证据，只是排序逻辑固定；SOP分数也有unknown和资格门槛。混为一项会制造“主分高=通过资格”。

建议：ScoreEnvelope明确 type/version/source；并排显示 marketing_opportunity 与 research_qualification，资格unknown时禁止自动进入测试池。主评分不替换、不改历史。

### C08 证据不能转为普通图片资源

证据：M:backend/main.py:234 清理24小时以上static；M:backend/services/storage_service.py 多公共目标；R:src/rabbit_hole/storage.py:57 起 manifest/hash/trust/原件管理；Compose启用版本且anonymous none。

建议：EvidenceRef仅含研究对象引用，通过鉴权流式下载；营销资产另存。缩略图/翻译/重绘标记为derived，禁止覆盖original，禁止给证据桶启用匿名读，迁移需同时核验DB引用与对象hash。

### C09 产品身份与时间/货币不同

证据：M:backend/db.py 的 int/history产品名；brand_context.js用户档案；R:src/rabbit_hole/workbench_domain.py:2167身份更新、verification.py:12指纹；workbench_markets.py七国，AGENTS规定核算为USD equivalents。

建议：source_system+project_id+product_id+identity_revision+source_version构成跨域引用；物理产品身份与品牌营销档案分开。UTC传输；研究country与文案language分开；金额必须带currency=USD、原币/转换来源可选，不能把GBP/JPY售价直接当美元。

### C10 配置热更新和进程观察差异

证据：M:backend/services/ai_config_service.py、binding为数据库快照；R:AISettings.resolve/private files在API/worker共享volume；R:src/rabbit_hole/config.py:get_settings缓存环境。

建议：首次集成不双写配置。主提供商变更只影响明确桥接任务；每研究动作冻结provider/model/route/config_version，缓存键包括模型版本/身份。明确外部服务只读不可用时不影响主配置加载。

### C11 全局JS/CSS碰撞与前端大文件

证据：M:frontend/js/app.js:5–23global state；index.html:5190起按顺序加载脚本；details.js/analysis.js有多模块交接。R:workbench-focus.js:3直接操作全局S；workbench.css与focused CSS面向独立页面。

建议：新research.js使用IIFE/单window.ResearchPanel，CSS全限定#researchView；只引入适配后的模块，保留主脚本顺序、原DOM IDs与草稿。不要把双方HTML整段插入。

### C12 网络、失败包装与命令恢复

证据：主多个生成API使用HTTP200+status:error（generation.py:33–121）；研究命令store.py:334–345处理409；API workbench有20秒业务超时，后台任务可能更久。

建议：统一新接口errors code/retryable/operation_id，不改旧API。GET可有限重试；commands使用原command_id与expected_version。提交后断线标outcome_unknown，查状态而非新建ID重发；409刷新并重新确认，不自动合并新状态。

### C13 平台、锁文件和测试差异

证据：主requirements未锁；SOPuv.lock，pyproject测试pytest<9；SOP文件模块fcntl；远端.venv interpreter断链。

建议：保持独立Python环境；后续生成主依赖基线锁只是提议需实施授权。研究服务保留Linux Docker；纯算法不带fcntl/Playwright。不能将“宿主Python3.9无法跑”当业务源码语法错误。

## 4. 风险登记表

| 风险 | 等级/暴露条件 | 应对措施 | 验收/停止条件 |
|---|---|---|---|
| 主工具功能回归 | 高：全局JS/DOM/路由变动 | 默认关闭research开关，增量新模块；旧端点契约/草稿/PDP/history回归 | 原功能新增失败即停止阶段，不以删功能修复 |
| 数据丢失/结构冲突 | 高：数据库硬合并、init_db升级、证据清理 | 不跨写库；SQLITE在线一致备份、PG及对象版本备份；先在副本演练 | 校验记录/引用/hash；任何缺失禁止切换 |
| API兼容/重复操作 | 高：409、HTTP200业务失败、超时重发 | version+command ID+digest；状态查询/人工重试；版本化DTO | 断线/同ID不同payload/两窗口测试通过 |
| 权限与秘密扩散 | 高：跨机proxy、LAN访问 | service credential+加密传输+路径白名单；浏览器session/CSRF；禁密钥透传 | 未授权读写/host伪造/任意URL代理全部拒绝 |
| 研究事实与营销混淆 | 高：AI推断变confirmed、旧身份沿用 | provenance/unknown/identity_revision/人工接受；双评分 | 过期/错商品/错国家/篡改quote不能进事实 |
| 外部计费与飞书重复写 | 高：叠加retry、outbox复启 | 查询状态、付费非幂等默认不自动重试；飞书单独开关 | 不确定结果不产生第二次收费/重复远端记录 |
| 依赖冲突 | 中：共用环境（pytest已有冲突） | 环境隔离；主依赖baseline；仅纯算法进主进程 | 独立锁/接口测试，无强制主升级 |
| 性能/内存 | 中：浏览器采集、截图/视频、大state与base64 | Playwright留远端；有界并发；小DTO分页/按需资产；无批量拉整个证据 | 队列/内存/主响应相对基线不恶化，阈值见05 |
| 后续维护 | 中：两个入口/DTO drift/两套providers | schema版本、服务所有权、contract tests、兼容窗口；阶段性合并纯能力 | 每域单写者；失联主功能可用 |
| 部署与网络 | 中：远端离线/镜像和源码偏差 | 健康/就绪区分；可降级研究面板；pin制品；明确Docker/tunnel恢复 | 远端关停主工具仍运行；版本不符禁止联调 |
| 迁移工作量 | 中：研究状态机及大JS复杂 | 8阶段小闭环；MVP只做0–3；高风险延期 | 每阶段验收后再进入下一阶段 |
| 备份与恢复不完整 | 高：只备DB忽略WAL/MinIO/private volume | DB+资产+私有配置独立备份、校验/恢复演练 | 未做restore演练，不进行DB/部署切换 |
| 时区/国家/金额误用 | 中：七国研究与USD equivalents | 显式country/language/currency/UTC；source_scope不降级 | 不同国家证据不得自动合并，美元字段必须明确 |
| 旧CLI/worker行为遗失 | 中：误判废弃或迁移所有loop | 保留旧入口，清点每job_kind与所有者，再逐项收敛 | 旧队列未盘点时不得停旧worker |

等级高表示潜在影响高，并不表示本次发现已经发生泄露、数据损坏或重复扣费。

## 5. 经济性与决策门槛

建议有条件推进（推断）：

- 先做“研究只读 + 人工确认 → 营销草稿”MVP，再判断真实使用频次；避免为一次性展示承担永久队列重构。
- 8阶段约28–45工程人日；0–3阶段MVP约13–19人日。估算假设1名熟悉Python/JS/数据库的工程师、权限/测试资源可获得、无新平台准入、无历史脏数据大规模修复；不是实测工期。
- 外部API套餐、额度、设备资源与业务收益本次未核价。不能据本报告计算投资回收期。
- 若不愿维护远端研究服务/PG/MinIO，先选择B的只读链接/摘要，不应改成A硬搬SQLite来降低表面部署成本。
- 若必须“一数据库、全部同进程、同时上线所有功能”，本评估不建议实施该目标；应重新立项并扩大测试/备份/权限设计范围。

## 6. 实施前仍须验证

1. 主未提交修改归属/稳定性；可回滚工作树快照与配置/资产范围。
2. SOP容器源码和依赖与当前HEAD/uv.lock一致，真实Alembic revision与所有消费者归属。
3. SQLite记录/资产引用与PG研究项目版本、状态分布；只记数量、摘要与hash，不泄露原文。
4. 私有桶匿名权限、对象版本、引用完整性、翻译缓存与provider-secrets恢复。
5. 固定版本集成接口的权限/错误/分页契约及网络运输方式。
6. 外部Meta/Trends/Firecrawl/AI/阿里云/飞书可用性及真实预算，需要用户主动授权有限样本；不能用health充当证明。
7. 真实性能和恢复耗时；本次仅语法和存活检查，没有全测试通过结论。
